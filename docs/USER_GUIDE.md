# User guide

## What does the agent do?

The agent provides only the current temperature for cities explicitly named in the
question. Examples:

- "What is the current temperature in Budapest?"
- "How warm is Vienna right now?"
- "What is the current temperature in London and Paris?"

It refuses forecasts, historical weather, humidity, wind, clothing advice, and
non-weather questions. If a request mixes allowed and disallowed information, the
agent refuses the entire request.

## Prerequisites

- Python 3.11 or newer;
- Bash on Linux or macOS, or Git Bash/WSL on Windows;
- an API key for OpenAI or an OpenAI-compatible provider;
- a model that supports tool calling;
- internet access to the LLM provider and Open-Meteo.

## Configuration

1. Copy the example configuration:

   ```bash
   cp .env.example .env
   ```

2. Open `.env` and set at least:

   ```dotenv
   OPENAI_API_KEY=...
   OPENAI_MODEL=gpt-5.6-sol
   ```

3. For another OpenAI-compatible provider, set its endpoint and a model available
   there that supports tool calling:

   ```dotenv
   OPENAI_BASE_URL=http://localhost:11434/v1
   OPENAI_API_KEY=not-needed
   OPENAI_MODEL=provider-model-name
   ```

The `.env` file is ignored by Git. Never commit an API key.

`OPEN_METEO_GEOCODING_LANGUAGE=en` controls the language used to rank and display
geocoding results. Override it when users commonly enter localized city names.

## Running the agent

The first run creates `.venv` and installs runtime dependencies:

```bash
./run.sh "What is the current temperature in Budapest?"
```

From Windows PowerShell, use the included wrapper instead of invoking the `.sh`
file directly:

```powershell
./run.ps1 --trace "What is the current temperature in Budapest?"
```

The wrapper locates Git Bash, forwards all arguments to `run.sh`, and returns the
same process exit code. Git for Windows must be installed.

A question may also be piped through stdin:

```bash
echo "How warm is Paris right now?" | ./run.sh
```

Useful options:

```text
--trace                 mirror trace events to stderr
--trace-dir DIRECTORY   override the JSONL trace directory
--model MODEL           override the model for this run
--base-url URL          override the provider endpoint for this run
--json                  emit a structured result for automation
--show-trace [TRACE]    display a trace by run ID, path, or "latest"
--html [OUTPUT]         create a self-contained trace dashboard
--help                  show complete CLI help
```

## Structured JSON output

Use `--json` when another program needs the validated temperatures and trace ID:

```bash
./run.sh --json "What is the current temperature in Budapest and Paris?"
```

The JSON document contains `status`, `answer`, `temperatures`, `errors`, `run_id`,
and the local trace path. It never contains an API key or a complete provider
response.

## Reading a trace

Every run automatically creates `traces/<run_id>.jsonl`. Each line is one
timestamped JSON event. Important events include:

- `reasoning_step`: a concise, auditable execution decision;
- `model_request` and `model_response`: LLM rounds;
- `tool_call_requested` and `tool_call_completed`: tool arguments and results;
- `run_finished` or `run_failed`: terminal state.

The trace contains neither API keys nor authorization headers. A `reasoning_step`
is not hidden model chain-of-thought; it is a concise description of the execution
path generated by the application. Every event also includes elapsed milliseconds,
while model and tool completion events include operation durations.

Display the latest run as a readable terminal timeline:

```bash
./run.sh --show-trace latest
```

Create an optional, self-contained local HTML dashboard:

```bash
./run.sh --show-trace latest --html trace-report.html
```

The HTML file contains no remote scripts, fonts, or analytics. Open it in a browser
to inspect run status, total elapsed time, model rounds, tool calls, and the complete
sanitized event timeline.

## Acceptance demonstration

The demonstration script runs an allowed single-city request, an allowed multi-city
request, and a rejected forecast request, then displays each trace:

```bash
./scripts/demo.sh
```

The script uses the same canonical `run.sh` entry point as normal operation.

## Output safeguards

The LLM decides whether to call the narrowly scoped temperature tool and selects
the city names. The application validates every selected city against the original
question. After the tool round trip, Python renders the public answer only from the
validated temperature payload. Model-generated text cannot add forecasts, humidity,
advice, or unrelated content. Without a validated tool result, the application emits
a fixed scope refusal.

## Troubleshooting

- `OPENAI_API_KEY is missing`: the value is missing or empty in `.env`.
- The model does not call the tool: select a model with function/tool calling support.
- An empty response after a successful tool call is retried once automatically and
  recorded in the trace; validated tool data remains available as a deterministic
  fallback.
- `City not found`: clarify the city name and include the country if needed.
- Provider failure: verify `OPENAI_BASE_URL`, `OPENAI_MODEL`, and the API key, then
  inspect the trace file printed by the CLI.
